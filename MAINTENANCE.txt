Memory-Microstructure-Analysis — 保守メモ(このリポジトリに手を入れる人向け)
================================================================================

README.md は「初めて読む人」だけに向けて書く。作業手順・命名規則・自分への
申し送りは README に書かず、このファイルに置く。GitHub のトップページで
レンダリングさせないため、拡張子は .md ではなく .txt にしてある。


1. 索引を必ず更新する
--------------------------------------------------------------------------------
目次は 2 段構えになっている。

    README.md                 リポジトリ全体の入口。銘柄一覧と主な結果
    reports/<COIN>/README.md  その銘柄の分析索引。レポート・図・数値データの全件

成果物を足したときに更新するもの:

    新しいレポート    reports/<COIN>/README.md の「レポート」節に 1 行。
                      A〜D のテーマ区分のどれかに入れる。
    新しい図          同 README の「図」表に 1 行。掲載レポートへのリンクを付ける。
    新しい数値データ  同 README の「数値データ」表に 1 行。生成スクリプト名を付ける。
    新しいスクリプト  同 README の「再現手順」に実行順で 1 行。
    新しい銘柄        reports/<COIN>/README.md を新規作成し、ルート README.md の
                      銘柄表のリンクを「未着手」から差し替える。

ルート README.md にはレポート件数を書かない。件数を書くと必ず古くなる
(実際に 5 のまま 12 本まで放置された)。件数が要るときは銘柄索引を見る。

ルート README.md のスクリプト表は接頭辞ごとの役割区分だけを保つ。
1 本ずつ列挙しない。列挙は銘柄索引の「再現手順」が持つ。


2. 書き方の作法
--------------------------------------------------------------------------------
- 図と表は、本文を読まなくても意味が取れるようにする。軸・単位・標本数・期間を
  図の中に書く。
- 数式は LaTeX で書く。GitHub の Markdown では行内が $`...`$、別行立てが
  ```math ブロックなら確実に描画される。$...$ と $$...$$ は環境によって崩れる。
- 推定値には必ず不確かさの幅と、その根拠になる検証(帰無対照・分割・多重比較の
  規模)を添える。「有意だった」だけで結論しない。
- 「予測」と「同時点の関係」を書き分ける。定義は reports/predicting_definition.md
  に一本化してあり、個別レポートで再定義しない。
- 費用(手数料・スプレッド・スリッページ)を引いた後の値で採否を語る。
- 誤りが見つかったら、訂正だけでなく経緯も残す。訂正の訂正も残す。


3. 先読みの禁止(最優先の制約)
--------------------------------------------------------------------------------
- 説明変数が確定する時刻 <= 目的変数の期間の開始時刻。窓 [T, T+d) の集計で
  同じ窓のリターンを説明しない(それは同時性であって予測ではない)。
- asof 結合は backward のみ。forward / nearest を説明変数に使わない。
- shift(-k) は目的変数専用。説明変数側に負のシフトを書かない。
- 標準化・分位・クリップ・欠損補完のパラメータを全標本から作らない。
- 標本外評価は時間ブロック分割で行う。行をシャッフルする k-fold は隣接窓が
  相関しているため漏洩する。
- 各スクリプトの docstring に「x が確定する時刻」と「y の期間」を明記する。
- 疑わしい箇所はプラセボ検定(説明変数を時間方向にずらす)で確認する。
- 板がクロスしている行(best_ask < best_bid)は必ず除外する。少数の異常行が
  係数を 16 倍動かした前例がある。


4. 図の配色
--------------------------------------------------------------------------------
配色を目視で決めない。次で検査し、合格しない配色は使わない。

    uv run python scripts/palette_check.py --colors "#xxxxxx,#yyyyyy,..."

明度帯・彩度下限・色覚特性下での分離・背景との対比を測る。系列が 5 本以上に
なると全対の色覚検査はまず通らない。そのときは色を増やさず、パネルを分ける。


5. 命名規則
--------------------------------------------------------------------------------
    scripts/inventory_*.py   作業用バケットの棚卸し
    scripts/fetch_*.py       必要な列だけを手元に落とす
    scripts/build_*.py       算出して data/ に書く
    scripts/plot_*.py        data/ を読んで charts/ に図を書く
    scripts/regress_*.py     回帰と散布図

    reports/<COIN>/<coin を小文字にしたもの>_<主題>_report.md
    charts/<銘柄コードの : を _ に置換>_<主題>.png     例 xyz_MU_book_slope.png
    data/<主題>_<銘柄>.csv       版管理する
    data/<主題>_<銘柄>.parquet   版管理しない(.gitignore 済み)


6. 版管理
--------------------------------------------------------------------------------
- 大きな中間生成物は data/**/*.parquet として除外済み。parquet はいつでも
  スクリプトで再生成できる状態を保つ。
- 図(charts/*.png)と、レポートが本文から参照する CSV は追跡する。
- 接続情報(バケット名・エンドポイント・鍵)はすべて環境変数から読む。
  値そのものをコード・ログ・レポート・コミットメッセージに書かない。


7. 実行
--------------------------------------------------------------------------------
    uv sync                        初回のみ
    uv run python scripts/xxx.py   常に uv 経由

システムの python では依存が入っていない。各スクリプトの docstring に
目的・入出力・実行例・時間契約が書いてある。
