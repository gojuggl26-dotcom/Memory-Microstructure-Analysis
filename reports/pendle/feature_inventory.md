## 11. 作れないもの(限界)

| 欲しいもの | なぜ無理か |
|---|---|
| **秒内の板の動き** | 粒度の下限は**ブロック**。同一ブロック内は `log_index` 順しか無く、それはログの出力順であってマッチング順の保証ではない |
| **ブロック内の真の因果順序** | 上に同じ。**サブブロックの因果を主張してはならない** |
| **`cancelled` の口座** | イベントに `account` が無い。同じ `order_id` の `placed` から**結合すれば取れる**が、`placed` が観測窓の外にある注文(孤児)は不明のまま |
| **`filled` の個別注文 ID** | `from_id`〜`to_id` の**範囲**しか無い。範囲内の全注文が消えるので数量は正しいが、「どの 1 本が」は範囲が広いと特定できない |
| **OTC の板への影響** | `otc_swap`(1.5%)は板を経由しない。**板の特徴量には現れない**取引が存在する |
| **AMM の連続的な状態** | 1 時間刻みのみ。イベント単位では見えない |
| **建玉の口座別内訳** | `notionalOI` は市場全体の 1 時間値。口座別は約定の累積で**推定**するしかない |
| **手数料・報酬の実額** | イベントに無い。帯の内外は API の `incentiveRange` で判る(#55)が、支払額そのものは判らない |
| **窓当時の報酬帯** | API は**現在エポックしか返さない**(`epoch` 系のパラメータを 4 通り試して全て無効)。過去に遡って当時の帯を知る公開経路が無い |
| **アーカイブ最終ブロック以降** | `extrapolated` フラグの区間。ブロック時刻が外挿になる |

## 12. 優先順位(私の推奨)

**すぐ効きそうな順**に並べる。根拠は「未使用の情報量が大きい」×「既存の結論に直接効く」。

1. **§5 ウォレット系(48〜55)** — `account` は 500 万件の `placed` すべてに付いている。
   市場 163 では**上位 2 口座で発注の 80.6%**。既存の全結論が
   「数口座の癖」を測っていただけという可能性を、これで初めて検証できる
2. **§5-55 報酬帯の内外** — README が全レポートで交絡として挙げ続けてきたもの。
   `iTickThresh` で分離できる。**これを潰さないと流動性指標の解釈が確定しない**
3. **§3-34 注文の生存時間**(order_id 結合)— 取消が 44.9% を占める板で、
   まだ寿命分布を一度も見ていない
4. **§4 キュー(42〜47)** — `order_index` は実測 0〜125。前方数量が作れれば
   約定確率の議論ができる
5. **§9-76 原資産のファンディング** — Boros の implied が**何を織り込もうとしているか**の
   当の系列。これ無しでは「予測できた」の経済的意味が定まらない
6. **§1-11〜14 距離帯・深度曲線・実効スプレッド** — 既存の `book_slope` は
   1 つのスカラーに潰しているので、形の情報を捨てている
7. **§10 AMM** — 網羅を確認したうえで。CLOB 単独の分析が
   「実際の流動性の一部しか見ていない」かどうかが判る
