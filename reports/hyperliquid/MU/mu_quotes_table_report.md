今後の分析の基礎データ。**1 行 = 1 つの発注候補**で、候補時点は BBO が更新された
瞬間(event-driven)、1 時点につき買い候補と売り候補の 2 行を作る。

最重要規則は **X_t は時刻 t までに観測可能な値だけ**。これをコードの読みで
済ませず、独立に計算し直して確かめた(§4)。

## 1. 列の一覧と「いつ確定するか」

説明変数はすべて **t 以前**に閉じている。窓は `(t−w, t]` で、境界は
「t ちょうどのイベントは含む・t より後は含まない」。

### 説明変数(45 列)

| 群 | 列 | 確定時刻 |
|---|---|---|
| 時刻 | `dt` `ts` `sec` | t |
| BBO | `bid` `ask` `mid` `spread_abs` `tick` `spread_bp` `spread_tick` | t(候補時点は BBO 更新時なので t の値そのもの) |
| BBO 状態 | `bbo_age_s`(前回の価格変化からの経過)`bbo_turnover`(直近 5 秒の更新回数/秒) | t 以前 |
| Side | `side`(+1 買い / −1 売り)`quote_px`(自分側の最良気配) | t |
| OBI | `obi1` `obi2` `obi4` `obi10`(累積 1/2/4/10 ティック)`obi_l2`(第 2 水準単独) | **t を含む 100 ms 格子セルの開始時刻**(§4-B) |
| 流動性 | `depth_own` `depth_opp` `depth_own_cum10` `depth_cum10` | 同上 |
| Queue | `queue_ahead_qty`(自分側最良の数量)`queue_ahead_est_cnt`(推定件数) | t |
| OFI | `ofi_0.1s` `ofi_0.25s` `ofi_0.5s` `ofi_1s` `ofi_10s` | 窓 (t−w, t] |
| Flow | `aggr_0.1s` `aggr_1s` `aggr_10s`(符号つきテイカー数量) | 窓 (t−w, t] |
| Hazard の入力 | `taker_rate_10s`(反対側テイカー流量/秒)`tau_hat_s = queue_ahead_qty ÷ taker_rate_10s` | 窓 (t−10s, t] |
| 流動性の動き | `fragility`(自分側の取消/累積板厚)`resilience`(同 追加)`touch_cancel_rate`(最良気配基準) | 窓 (t−10s, t] |
| Risk | `rv_60s_bp`(1 秒刻み 60 秒の実現ボラ)`ofi_var_60s` | t 以前の最後の秒境界まで |
| Regime | `hour_utc` `is_us_session` `is_weekend` | t |

**`Hazard` そのもの(予測約定確率)はこの表に入っていない。**モデルの出力なので、
この表を訓練データにして当てはめる必要がある(= Step 2)。ここではその入力である
`tau_hat_s` と、実現値である `label_fill_lat_s` を持たせてある。

### ラベル(9 列・**未来を使う**)

| 列 | 定義 |
|---|---|
| `label_filled_60s` | 60 秒以内に約定したか(0/1)。**打ち切りは 60 秒** |
| `label_fill_lat_s` | 約定までの秒数(未約定は null) |
| `label_edge_bp` | 約定直前(τ−2 ms)の mid と自分の指値の差。符号つき bp |
| `label_markout_{0.1,1,10}s_bp` | 約定後の mid 変化(自分に有利が正) |
| `label_pnl_{0.1,1,10}s_bp` | `label_edge_bp − 0.088 + markout`(メイカー手数料控除後) |

## 2. 数値の概観

### 約定

| | 値 |
|---|---|
| 60 秒以内の約定率 | **62.14%**(分母 = 全 70,338,666 行) |
| 買い候補 / 売り候補 | 62.11% / 62.16%(ほぼ対称) |
| 約定までの秒数 | 中央 **8.85 秒** / 平均 14.88 秒 |

### 損益(約定した行のみ・分母 4,370 万行)

| | 平均 | 中央 |
|---|---:|---:|
| `label_edge_bp` | **−2.739** | −1.146 |
| `label_markout_1s_bp` | −0.929 | −0.491 |
| **`label_pnl_1s_bp`(手数料控除後)** | **−3.756** | −2.316 |
| `label_pnl_10s_bp` | −4.061 | −2.862 |

**無条件に最良気配へ置き続けると大きく負ける。**日次平均で見ても
**98 日中 97 日が負**(唯一の例外 2026-05-09 はスプレッド中央値 6.57 bp と
期間中で最も広く、約定率も 43.9% と低い日)。これは既報
`mu_cancel_bt_report.md` の「22 通りの EV 設定すべての 95% 信頼区間が 0 未満」と
同じ向きの結論で、今回は候補の作り方(1 秒格子 → BBO 更新ごと)を変えても
覆らないことを示している。

### 既報との突き合わせ

`label_edge_bp` は「発注時の半スプレッド + 約定までの mid ドリフト」に分解できる。

| 約定までの上限 | 発注時の半スプレッド | 実現エッジ | 含意されるドリフト r(T→τ) |
|---|---:|---:|---:|
| 10 秒 | +0.733 | −1.291 | **−2.024 bp** |
| 60 秒 | +0.790 | −2.740 | −3.531 bp |

既報 `mu_markout_report.md` の A 成分(寿命 10 秒での r(T→τ))は **−1.618 bp** で、
向きと桁は一致するが**値は一致しない**(−2.024 対 −1.618)。原因は定義の違いで、
既報は「1 秒格子で発注し 10 秒で取り消す」設定の全発注が対象、今回は
「BBO 更新ごとに発注し 10 秒以内に約定した行」に条件づけている。後者は
板が活発な瞬間を多く拾う(既報 `mu_burstiness_report.md` で指摘した偏り)。
**同一の量ではないので、どちらかが誤りという話ではない。**混同しないよう
Step 2 以降では出典を明記して使う。

## 3. 標本は期間内で均質でない(重要)

図 `xyz_MU_quotes_daily.png`。

| | 前半 49 日 | 後半 49 日 |
|---|---:|---:|
| 候補行数(計) | 26,543,972 | 43,794,694(**1.65 倍**) |
| 約定率 | 54.96% | 66.49% |
| スプレッド中央値 | 2.34 bp | 0.98 bp |

98 日を 1 つの母集団として平均すると、行数の多い後半に重みが寄る。
**期間で層別するか、日次で集計してから日を単位に評価すること。**
標本外評価は既定どおり時間ブロック分割で行う(行のシャッフルは禁止)。

なお図 (a) の周期的な谷は週末である(`is_weekend` で分離できる)。

## 4. ルックアヘッド監査

「コードがそう書けている」だけでは足りないので、3 通りで確かめた。
標本日は前・中・後から機械的に選んだ **2026-05-07 / 06-22 / 08-06**、
各日 3,000 行(乱数種固定)。スクリプトは `scripts/audit_quotes.py`。

### A. 独立再計算 — 一致

窓の端を二分探索で決めて**スライスをそのまま足す**経路(表の生成は累積和の差分)で
6 列を計算し直した。3 日 × 6 列すべてで**相対差 5×10⁻⁸ 以下**、これは float32 の
丸め幅そのものである。窓の端が 1 つでもずれていれば必ず食い違う。

対象: `aggr_1s` `cancel_10s` `add_10s` `ofi_1s` `spread_bp` `queue_ahead_qty`

### B. 板の時刻 — 先読みしていない

多水準の板は 100 ms 格子で再構成しており、これが未来を含むと全 OBI/depth が汚染される。
そこで `depth_own` が「セル開始時刻の bbo」と「t 時点の bbo」のどちらに一致するかを見た。
**両者が食い違う行だけ**が識別力を持つので、それに限って集計する。

| 日 | 食い違う行 | セル開始時点と一致 | t 時点と一致 |
|---|---:|---:|---:|
| 2026-05-07 | 1,495 | **88.03%** | 1.20% |
| 2026-06-22 | 1,952 | **77.05%** | 0.10% |
| 2026-08-06 | 2,028 | **76.58%** | 0.25% |

板はセル開始時刻(= t 以前)の状態である。**古さは中央 50 ms・最大 100 ms**。
残る 12〜23% の不一致は再構成そのものの誤差(`build_obi_levels` が
`l1ok` として計測している既知の量)で、時刻の問題ではない。

### C. 陽性対照 — 検定力は限定的(正直に書く)

「漏れていたら気づけるのか」を確かめるため、**わざと未来を使った特徴量**
(今後 60 秒の反対側テイカー流量 — 約定を機械的に決める量そのもの)を作って
約定の判別力を比べた。

| 日 | 後ろ向き `ofi_1s` | `queue_ahead_qty`(符号反転・正当) | **未来 60 秒の流量(意図的な漏れ)** |
|---|---:|---:|---:|
| 2026-05-07 | 0.4404 | 0.6259 | **0.7906** |
| 2026-06-22 | 0.3993 | 0.6993 | **0.7359** |
| 2026-08-06 | 0.3929 | 0.6987 | **0.6910** |

漏れは AUC を 0.69〜0.79 まで押し上げるので、検定は**強い漏れなら検出できる**。
ただし正当な `queue_ahead_qty` が 0.63〜0.70 と拮抗し、08-06 では**正当な変数が
漏れを上回っている**。したがってこの対照だけで「漏れがない」とは言えない。
**根拠の主体は A と B であって、C は補助である。**

## 5. 既知の限界(使う前に読むこと)

1. **板は最大 100 ms 古い。**ブロックが約 65 ms 周期なので実質 1〜2 ブロック。
   サブ 100 ms の議論には使えない。
2. **fills の時刻はミリ秒精度**で、板イベント(ns)より最大 ~1 ms 早い。
   サブミリ秒の因果順序を主張しない。約定は「その時刻以降で最初のイベント」に割り当てる。
3. **`label_filled_60s` は 60 秒で右打ち切り。**60 秒を超えて約定する注文は
   「未約定」として記録される。生存時間の分析では打ち切りとして扱うこと。
   同様に、日の終端近くの候補は markout の窓が日をまたげないため null になる
   (`label_markout_10s_bp` の欠損が 0.01 pp だけ多いのはこれ)。
4. **`obi_l2` は 20.34% が欠損。**第 2 水準が空(板が薄い)ときに定義できない。
   累積の `obi2` は第 1 水準を含むので欠損しない。
5. **`tau_hat_s` に `inf` が入る。**直近 10 秒に反対側テイカーが 1 件も無いとき。
   これは「観測範囲では約定しない」という情報であって欠損ではないが、
   そのまま回帰に入れると落ちる。Step 2 で上限打ち切りか逆数化が要る。
6. **`fragility` / `resilience` / `touch_cancel_rate` は裾が極端に重い**
   (中央 9.7 に対し最大 8.8×10¹³)。分母の板厚が薄いときに発散する。
   対数化か分位打ち切りが前提。
7. **候補時点が BBO 更新に張り付いている**ため、板が活発な時間帯を過剰に拾う。
   時計時間で等間隔に評価したい問いには、この表をそのまま平均してはいけない
   (`mu_burstiness_report.md` の指摘と同じ)。
8. **費用はメイカー手数料 0.088 bp/約定のみ控除**している。テイカー手数料・
   資金調達・スリッページは入っていない(最良気配に置く前提なのでスプレッドは
   `label_edge_bp` に内在する)。

## 6. 訂正の記録

この表を作る過程で自分の誤りを 3 つ見つけた。経緯ごと残す。

**(1) NaN と null の混在(データ側・修正済み)**
「該当なし」を NaN で表していたため、polars の `mean` は NaN を伝播し
`median` は無視する、という不整合が出た。さらに polars は **NaN を最大値として
順序づける**ので、`|obi1| > 1` の異常検出が 496 件、`label_fill_lat_s` の
範囲外検出が 2,663 万件と、**すべて偽陽性**になっていた。
全 float 列の NaN を null に統一して解消(`scripts/fix_quotes_nan.py`)。
影響: 統一前の `label_edge_bp` 日次中央値は **+0.110**、統一後は **−1.033**。
符号が反転しており、気づかずに出していれば結論を誤っていた。

**(2) `float(x or np.nan)`(集計スクリプト・修正済み)**
0.0 は偽値なので、**中央値が 0 の列がすべて「欠損」として表示されていた**
(`ofi_*` `aggr_*` `bbo_age_s` `is_weekend` など 12 列)。値そのものは無事。

**(3) 監査スクリプトの単位取り違え(監査側・修正済み)**
`depth_own` は既にサイズ単位なのにロット換算を掛け、§4-B の一致率が
両方 0.00% と出た。「両方 0%」は検定側の誤りを示す典型なので、
結論を出す前に実値を見て気づけた。

生成そのものも 3 度止まっている。1 度目は他プロセスと競合してメモリ不足
(bbo 3,517 万行と fills を常駐させていたのを日ごとの遅延読み込みに変更)、
2・3 度目は解放処理が進捗表示の参照する変数まで消していたため。いずれも
書き出し後に落ちており、**破損ファイルは無く**(全 98 日を読み直して確認)、
済んだ日を飛ばす再開機構で欠損なく完走した。

## 8. 次(Step 2)

この表を訓練データにして `Hazard`(予測約定確率)を当てはめる。
**訓練期間だけで標準化・分位・欠損補完のパラメータを推定し**、
評価は時間ブロック分割で行う。§3 のとおり期間内で標本の性質が変わるので、
単純な前半/後半分割では訓練と評価の分布が揃わない点に注意が要る。
