## 1. 【実施 1】東京 EC2 の実測 — 前回の分析を撤回する

ap-northeast-1c に t4g.micro を立て、同じ測定コードを走らせた(所要 10 分、費用 < \$0.01、測定後に
インスタンス・SG・鍵をすべて削除済み)。

| 経路 | この機械(日本・家庭回線) | 東京 EC2 | 改善 |
|---|---|---|---|
| TCP → api.hyperliquid.xyz | 16.7 / 30.8 / 111.7 ms | 2.31 / 2.49 / 4.30 | 7.2× / 12.4× / 26× |
| TCP → fapi.binance.com | 17.1 / 30.0 / 53.4 | 2.50 / 2.72 / 8.75 | 6.8× / 11× / 6.1× |
| HTTP `POST /info` (HL) | 85.8 / 107.5 / 248.6 | 13.17 / 14.78 / 261.69 | 6.5× / 7.3× / 1.0× |
| HTTP `GET /fapi/v1/time` | 86.0 / 99.0 / 177.8 | 11.52 / 12.61 / 18.88 | 7.5× / 7.9× / 9.4× |
| 時計ずれ(Binance 基準) | +132.4 ms(sd 6.9) | +4.27 ms(sd 1.27) | 31× |

(min / p50 / p99)

### ★撤回

前回「TCP 16.7 ms なのに HTTP 85.8 ms、差の ~69 ms は API 層の処理だから東京に行っても削れない」
と書いたが、誤りだった。東京 EC2 の HTTP は 13.2 ms で、
その ~69 ms のうち ~85% は経路の往復だった。TCP が速く見えたのは
CloudFront のエッジで終端していたためで、エッジ → オリジンの往復を見ていなかった。
東京 AWS は読み経路を 6.5 倍速くする。

### 副産物 2 つ

- HL の API は裾が悪い: 同じ箱から Binance の p99 が 18.88 ms なのに、HL は 261.69 ms(14 倍)。
  中央値では 14.78 vs 12.61 とほぼ互角なのに、裾だけが桁違いに悪い
- 時計精度: 適切に同期された箱は 4.3 ms(sd 1.27)。取引所はこれ以上に厳密なはずなので、
  報告 44 の 200〜250 ms のラグを「時計ずれ」で説明するのは苦しい → 報告 44 の結論を補強する
  (同時に、報告 45 の「片道 ≈ 222 ms」は私の壊れた時計に基づく値だったので信頼できない)

## 2. 【実施 3】Binance 信号のバックテスト

報告 44 の信号を退出規則として既存エンジンに実装した(`rest_policy_bn.py`)。

```
時刻 t に知っている Binance = t − 100ms まで(報告 45 の実測読み遅延)
その直近 250ms の対数リターン sig を見て
    sig < −thr → 買い気配を引く    sig > +thr → 売り気配を引く
引いた側は t + hold まで再発注しない。取消も lat_cancel だけ遅れて効く
```

検算: 信号を無効(thr=∞)にすると `rest_policy.simulate_rest` と
遅延 0ms・100ms の両方で完全一致(損益 1e-9 以内、約定数も同一)。

### 結果(30 日、k=0)

| 遅延 | 信号なし | 信号あり(2bp/500ms) | 信号の効果 | p |
|---|---:|---:|---:|---:|
| 0 ms | +4.825(22/30) | +4.946(24/30) | +0.121 | 0.756 |
| 25 ms | −2.783(7/30) | −1.252(10/30) | +1.531 | 0.0086 |
| 50 ms | −2.739(6/30) | −1.337(10/30) | +1.403 | 0.0074 |
| 75 ms | −2.416(7/30) | −1.047(10/30) | +1.369 | 0.0516 |
| 100 ms | −2.512(5/30) | −0.829(12/30) | +1.684 | 0.0061 |

閾値・保持時間のスイープ(遅延 100ms):

| 閾値 | 保持 | E[PnL] | 対照との差 | p | 引き/日 |
|---|---|---:|---:|---:|---:|
| 1 bp | 500ms | −0.428 | +2.084 | 0.0131 | 29,486 |
| 2 bp | 250ms | −1.066 | +1.446 | 0.0060 | 10,411 |
| 2 bp | 500ms | −0.829 | +1.684 | 0.0061 | 9,803 |
| 2 bp | 1000ms | −1.319 | +1.193 | 0.0521 | 8,498 |
| 4 bp | 500ms | −2.014 | +0.498 | 0.0843 | 3,080 |

読み取れること:

1. 信号は本物。遅延 25/50/100 ms のすべてで有意に改善し(p=0.006〜0.009)、
   効果量も +1.4〜1.7 と安定。4 つの独立な遅延設定で一貫していることが、
   個別セルの p 値より強い証拠である
2. 遅延 0 ms では効かない(+0.12、p=0.756)。当然で、無限に速ければ早期警報は要らない。
   信号の価値は遅さの保険であり、その理屈どおりに振る舞っている
3. しかしゼロを超えない。最良で −0.83 USD/日、ゼロとの検定 p=0.356、黒字 12/30
4. 多重比較: 探索 10 セル → Bonferroni 閾値 0.0050。最良 p=0.0060 でわずかに届かない
5. 閾値 1bp は引きすぎ(遅延 0ms では対照より −1.065、p=0.023 で有意に悪化)

## 3. ★崖の発見 — 東京に行っても届かない

遅延を細かく刻むと、E[PnL] はなだらかに落ちない:

```
  0 ms : +4.83   ←──┐
 25 ms : −2.78   ←──┘ ここで崖
 50 ms : −2.74
 75 ms : −2.42
100 ms : −2.51
```

線形内挿すると損益分岐は 信号なし ≈ 16 ms / 信号あり ≈ 20 ms。

ここで報告 45 の測定と突き合わせる:

| 遅延の内訳(東京 EC2 + 最善の実装) | 値 |
|---|---:|
| ネットワーク往復 | 2.5 ms |
| API 処理(読み) | ~11 ms |
| ブロック取り込み待ち(平均) | 33〜35 ms |
| 合計 | ≈ 47 ms |

> ブロック待ちだけで崖(16〜20 ms)を越えている。
> これは実装の問題ではなく HyperBFT のブロック時間(65〜70 ms)そのもので、
> 誰も回避できない(注文送信は API を迂回できないことも確認済み)。
>
> したがって「遅延 0 ms の +4.83 USD/日」は、原理的に到達不能な数字だった。

崖の機構は逆選択そのもので説明がつく。最良気配が動いた瞬間から数 ms で不利な約定が来るため、
一度でも遅れれば損害はほぼ確定し、そこからさらに遅れても大きくは変わらない
(報告 16: 逆選択が粗利の 79% を奪う / 報告 44: 情報は 200 ms で伝播する)。

## 4. 【実施 2】書き経路の測定 — 手順と金額(未実施)

実弾が要るので私は発注していません。 手順は以下:

| 項目 | 内容 |
|---|---|
| 目的 | 「送信 → 板に現れる」の実測。Glassnode の 884 ms が書き経路の実体か確認する |
| 方法 | 最良気配から 50〜100 ティック離れた位置に最小数量の ALO を置き、`POST /exchange` 送信時刻と、自前ノード or WS で自分の注文が板に現れた時刻の差を取る。直後に取消 |
| 約定リスク | ALO かつ遠隔価格なのでほぼゼロ。万一約定しても最小数量(0.1 単位 ≈ 5.8 USD) |
| 費用 | 手数料は約定しなければ 0。必要証拠金として 20〜50 USD 程度あれば足りる |
| 回数 | 100〜200 回で分布が出る。アドレスのレート予算(初期 10,000)で十分 |
| 人間の作業 | API ウォレット(agent)の作成と秘密鍵の用意。CLAUDE.md の秘密取扱いに従い、私は鍵に触れません |
| 併せて測るべき | 取消の「送信 → 板から消える」も同じ手順で。メイカーにとってはこちらが本命 |

この測定が最優先である理由: §3 の崖の位置(16〜20 ms)に対し、
書き経路が 40 ms なのか 380 ms なのか 884 ms なのかで、
「どれだけ絶望的か」の桁が変わる。ただしどの値でも崖は越えているので、
結論そのものは変わらない見込み。

## 5. 何をすべきか

東京 AWS への移行そのものは正しい。 ただし理由が変わる:

- ✗ 「この戦略を黒字にするため」ではない。崖の手前に届かないので不可能
- ○ 測定基盤として正しい。時計精度 4.3 ms は報告 44/45 のような測定の前提条件で、
  現在の開発機(132 ms ずれ)ではまともな時刻測定ができない
- ○ 報告 40 の B(上場初期マーケットメイク)には効く可能性がある。
  初期は半スプレッドが δ\ の 38 倍あるので、崖の位置がまったく違うはず。
  崖の位置を上場初期で測り直すのが次の一手

低遅延ノード(32 コア/128GB、月 \$1,000〜1,100)は、まだ立てるべきでない。
成熟期 DRAM では崖を越えられないことが確定したので、投資の根拠は
「上場初期で崖の位置を測る」→「複数市場を回せる目処」の順でしか作れない。

## 6. 自己精査

- ★自分の分析を 1 つ撤回した(§1)。前回「コロケで削れるのは ~17 ms」と書いたのは、
  CloudFront エッジ終端を見て「TCP が速い = 近い」と誤解したため。
  実測で 6.5 倍の改善と判明。推論ではなく測定に置き換えた
- エンジンの検算: 信号無効時に既存実装と 1e-9 以内で完全一致(§2)
- §B-5 対照の設計: 主判定を「信号あり vs 信号なし(同一方策)」に置いた。
  ゼロとの比較は補助として併記。ベースライン依存で自動成立しない形
- §C-10 多重比較: 10 セル・Bonferroni 0.0050 を明示し、最良 p=0.0060 が届かないと書いた
- §C-9: 信号を「効果なし」とはせず、「有意に効くがゼロを越えない」と分けた
- §D-16 実装可能性: 退出規則は各時点で計算できる形(直近 250ms の Binance リターン)
- 費用規律: 東京の測定資源(インスタンス 3 台・SG・鍵)はすべて削除確認済み
