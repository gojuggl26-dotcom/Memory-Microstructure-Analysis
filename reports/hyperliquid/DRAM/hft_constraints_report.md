## 1. 物理制約 — 遅延・ブロック・優先手数料

### 1-1. 地理と到達遅延

- バリデータは 24 基すべて AWS 東京(ap-northeast-1)の複数 AZ。東京からの到達は 2〜3ms、欧米からは +200ms 超(CoinDesk 2026-03-30)
- ただし order-to-fill(発注→約定確認)は東京 AWS からでも中央値 884ms(範囲 695〜1,634ms、n=120、2026-03、Glassnode)。内訳はネットワーク ~5ms + サーバ側 ~879ms。公式の公称値(中央値 0.2s / p99 0.9s)より大幅に遅い
- 自前の L4 データでの実測: BBO 更新間隔 p10 54.5ms / p50 82.7ms(成熟期)= ブロック間隔。取消・約定はブロック単位でしか効かない(1ms 窓と 10ms 窓の窓数が同一 — `cancel_report.md`)

### 1-2. ブロック内の処理順序(2026-04-13 の優先手数料と同時に明文化)

同一ブロック内は 3 クラスの順で処理される: ① 流動性を取れない注文(ALO)→ ② 取消 → ③ テイカー可能な注文。

- 取消は同ブロックのテイカーに絶対に抜かれない(優先料でも不可)。我々のシミュレーションは取消とテイカーを対称に扱っていたので、この点だけは悲観側に測っていた(唯一の有利側の誤差)
- ALO は各価格レベルで「直近 T=400ms に置かれた注文」のコホート内を優先料率の降順で並べ替える。時間優先が 400ms 単位で入札制に変わった

### 1-3. 優先手数料の実額(2026-04-13 導入、以降 4 ヶ月で \$5.07M 徴収)

| 種類 | 買えるもの | 課金 |
|---|---|---|
| gossip 入札(読み) | データ受信 ~25ms/枠。ダッチオークション、3 分周期、床 0.1 HYPE、落札後は前回価格の 10 倍から再開 | HYPE 焼却(入札時) |
| IOC 優先料(書き) | 1bp ≈ 45ms の遅延短縮、上限 8bp(それ以上は同格内タイブレーク)。HIP-3 資産の IOC が対象 | 約定 notional のみ |
| ALO 優先料(書き) | 400ms コホート内のキュー順 | resting notional に、未約定でも課金 |

我々にとっての含意 3 つ:
1. 敵のテイカーは ~8bp 払えば ~360ms ぶん速くなれる。stale 気配の食い取り(数 bp の利得)に対し数 bp の優先料は割に合うので、払われる前提で考えるべき。レースは一段と不利になった
2. ALO 優先料を我々が使う選択肢は論外: 埋まり率 1〜2% で placement ごと課金のため、1bp 付けると日次 resting notional 6.3M USD(テスト資金構成)〜14.2M USD(Q=1)× 1e-4 = 630〜1,420 USD/日。E[PnL](5〜8 USD/日)の 100 倍超
3. 逆に「置いて 400ms 経過した注文の順位は買収不能」— 長く置く方策(k≥2)はコホート入札の外側にいられる。報告 37 の結論を制度が補強する

### 1-4. 自前の遅延感度(報告 35、テスト資金構成、30 日中央値)

| 遅延 | 0ms | 50ms | 100ms | 300ms |
|---|---:|---:|---:|---:|
| E[PnL] USD/日 | +2.53 | −0.61 | −0.20 | +0.96 |

非単調である。50〜100ms = 「レースに参加して負ける」帯、300ms = 事実上の置き方策。
現実に到達可能なのは(東京 + 自前ノード + gossip 入札でも)100ms 台以深なので、
速度依存の設計は最悪の帯に着地する。§6 の方針はすべてこの表から出発する。

## 2. 規則の制約 — レート制限の実仕様 ★報告 33/34 の訂正

### 2-1. 仕様の全文(公式 docs、2026-08-18 時点)

| 層 | 規則 |
|---|---|
| IP(REST) | 合計 weight 1,200/分。exchange 系は weight = 1 + floor(バッチ長/40) → バッチで実質無制限 |
| WebSocket | 10 接続/IP、新規 30 接続/分、購読 1,000、メッセージ 2,000/分、inflight post 100 |
| アドレス(L1 アクション) | 累積 1 リクエスト/1 USDC 取引 + 初期バッファ 10,000。超過後は 1 リクエスト/10 秒 |
| 同・取消の特例 | 取消の上限 = min(limit + 100,000, limit × 2) — 詰まっても引くことだけはできる |
| 同・バッチの数え方 | IP には 1 件、アドレスには n 件(バッチはアドレス予算を節約しない) |
| open orders | 1,000 件(+1 件/5M USDC 出来高、上限 5,000)。1,000 件超で reduce-only/トリガー拒否 |
| 混雑時 | ブロックスペースの割当 = 前日メイカーシェアの 2 倍まで |
| expiresAfter | 失効した action は通常の 5 倍をアドレス予算から消費 |
| scheduleCancel(デッドマンスイッチ) | 5 秒以上先を指定、発火は 10 回/日まで |
| API ウォレット | 無名 1 + 記名 3(サブアカウントごとに +2) |

### 2-2. ★「6.6 操作/秒」は実在しない

報告 33 §4 以降の判定に使った「上限 6.6 操作/秒(取引所仕様)」に相当する固定レートは、
現行仕様のどこにもない(監査台帳 #10 が「未再検証」と警告していた項目。本調査で解消)。
実在するのは (i) IP 1,200 weight/分 = 20 リクエスト/秒(バッチで回避可能)と
(ii) 上記の出来高連動のアドレス予算である。

### 2-3. 実仕様での再判定(本報告の新規計算)

持続条件は「アクション消費/日 ≤ 自分の約定 notional USDC/日」。
解釈が 2 つありうるので両方で判定した(`data/DRAM/rate_limit_real.csv`):

- A(保守): 取消も同一カウンタを消費(取消特例は天井が高いだけ)→ 発注+取消 ≤ 出来高
- B(緩い): 取消は別枠 ≈ modify(取消+再発注を 1 アクションに置換)で実装した場合の必要条件

テスト資金 100 USD(Q=0.37、約定 ~8.6 万 USD/日) — 消費/出来高比の中央値と超過日数/30:

| k | A 中央値(超過日) | B 中央値(超過日) |
|---|---:|---:|
| −1(旧方策) | 4.84(30) | 2.45(30) |
| 0 | 2.95(30) | 1.50(24) |
| 2 | 2.33(29) | 1.19(21) |
| 5 | 1.52(26) | 0.79(6) |
| 10 | 0.92(11) | 0.48(0) |
| 20 | 0.56(1) | 0.31(0) |

Q 別(k=−1 の無駄あり方策のまま):

| Q | 約定 USD/日 | A 中央値(超過日) | B 中央値(超過日) |
|---:|---:|---:|---:|
| 1 | 303,958 | 1.87(30) | 0.95(9) |
| 5 | 1,240,541 | 0.48(0) | 0.24(0) |
| 10 | 2,147,009 | 0.28(0) | 0.14(0) |
| 50 | 6,772,041 | 0.09(0) | 0.05(0) |

読み方: 発注数はサイズにほぼ依存しない(33〜35 万/日)が、予算の獲得源(自分の約定 notional)は
サイズに比例する。ゆえにこの制限は小口を殺し、大口を通す。

- 報告 33/34 の「全サイズで実行不能(116〜122%)」→ 撤回。正: Q≥5 はどの解釈でも余裕
- 報告 34 の「テスト資金 100 USD で運用」→ 実仕様でも不能(k≤5 は大半の日で予算超過。
  k≥10 なら通るが、その領域の E[PnL] はゼロと区別できない — 報告 37)
- Q=1 は境界線上: k=2 + modify 実装(B)で 0.95 × 0.59 ≈ 0.56 → 可。
  cancel+place 実装(A)のままだと 1.11 で不可
- 報告 37 の k=2 推奨は理由が変わる: レートのためでなく、E[PnL] +50% とコホート入札回避のために採用

### 2-4. 対策(規則側)

| 対策 | 効果 | 注意 |
|---|---|---|
| modify / batchModify で建て直す | アドレス予算 2 → 1(発注+取消の対を 1 アクションに) | queue 位置は失う(価格を変えるときだけ使うので無害) |
| バッチ発注 | IP weight を 1/40 に | アドレス予算は減らない |
| 予算のプレバンク | 予算はアドレス生涯累積 — 過去に出来高のあるアドレスは貯金がある | 自己売買での予算稼ぎは STP(selfTradeCanceled)で不可能。手数料を払って対当銘柄でテイクすれば貯まるが、費用対効果は要計算 |
| expiresAfter は付けない | 失効 1 件 = 5 件分の予算消費 | デッドマンスイッチは scheduleCancel で(発火 10 回/日以内の設計に) |
| 混雑条項の考慮 | 前日メイカーシェア 2 倍のブロックスペース | 新規参入の初日はシェア 0 — 混雑日に締め出される。§6-B の上場初日戦略はここが要検証 |

## 3. 経済の制約 — 手数料・funding

### 3-1. 手数料の実測と公式表の照合

実測(報告 16、成熟期 10 日、154 万メイカー約定): taker 合計 0.846bp =
取引所 0.543 + deployer 0.227 + builder 0.076。maker は 0.088bp の支払い(リベートなし)。

公式表(trade.xyz、tier 0): 標準モード taker 9bp / maker 3bp。growth mode で 1/10(taker 0.9 / maker 0.3bp)。
実測が公式 tier 0 の growth mode 値よりさらに低いのは、出来高 tier(〜tier 6 で maker 0)と
HYPE ステーキング割引(5〜40%)の加重平均だから。照合は整合。

- live API 確認(2026-08-18): `growthMode: "enabled"`、`deployerFeeScale: 1.0`、
  xyz の 114 資産中 110 が growth mode。fee scale 最終変更 2026-04-22(上場前から不変)
- builder fee 0.076bp は自前 API 発注なら払わない(フロントエンドの builder code 由来)。
  既報の E[PnL] は maker 費用しか引いていないので数字は変わらない

### 3-2. ★体制リスク: growth mode は 30 日ごとに消せる

growth mode の on/off は資産ごとに 30 日に 1 回変更できる(2025-11-19 導入、trade.xyz は当日有効化)。
切られた場合 maker 0.088 → ~0.88bp(10 倍)。損益分岐は

```
δ* = f + βσΔ = 0.088 + 0.275 = 0.363bp   (現行、報告 36)
δ*_標準 ≈ 0.88 + 0.275 ≈ 1.16bp           (growth mode 終了後)
```

達成可能な δ は k=0 で 0.271bp、深く置いても 0.440bp、ハーフスプレッド中央値 0.62bp。
growth mode が切られた瞬間、この市場のメイカー経済は全滅する。
対策は「前提の監視」以外にない: `meta` の `growthMode` / `lastFeeScaleChangeTime` を定時取得し、
変化したら即時全取消・撤退する運用条項を最初から書いておく。

### 3-3. funding(本報告の新規実測: 99 日・2,360 時間)

| 統計 | 全期間 | 評価窓(07-10〜08-08) |
|---|---:|---:|
| 時間 funding 中央値 | +1.5e-5(+0.15bp/h) | — |
| 平均(年率換算) | +3.3e-5(+28.6%/年) | +1.6e-5(+14.4%/年) |
| 正の時間の割合 | 84.8% | 88.1% |
| 自己相関(1h/6h/24h) | 0.42 / 0.25 / 0.11 | — |
| max \|funding\| | 33bp/h(仕様上限は 4%/h) | — |
| premium(mark−oracle) | 平均 +6.5bp、\|中央値\| 7.2bp | — |

- MM への影響は小さい: 在庫上限 5Q に張り付き続けた場合の上界で
  292.5 USD × 7.8bp/日 ≈ 0.23 USD/日(Q=1)。E[PnL] の 3〜5% 未満
- ただし市場の体制として「ロングが年率 ~29% 払い続ける」= 群衆はロング側。
  premium の恒常乖離(7.2bp)はスプレッド(1.23bp)の 6 倍あり、
  mark 回りの統計(清算・funding)は板の中値と別物として扱うこと
- 現物ヘッジは存在しない(DRAM 指数は直接取引不能)。short-carry は
  「funding を貰って群衆の反対側の価格リスクを裸で持つ」取引であり、裁定ではない

## 4. 構造の制約 — HIP-3 と DRAM 固有

- deployer(trade.xyz)の権限: オラクル定義・レバレッジ・手数料 scale・
  haltTrading(全注文取消 + mark 価格で強制決済)。ステーク 500k HYPE(≥183 日維持)と
  スラッシング(不正 state 遷移で最大 100%)が抑止だが、単一主体依存は消えない。
  ここに置く資本は「取引所リスク + deployer リスク」の二重
- オラクルは live 更新(本調査で実測: 20 秒間隔の 2 標本で 58.46 → 58.48 と変化。
  更新間隔 ≤20s とだけ言える)。日次指数の懸念は否定された
- DRAM の現在値(live API 2026-08-18): OI 1.43M 単位 ≈ 83.5M USD、
  出来高 247.5M USD/日(評価窓中央値 227M と同水準 — 市場は縮んでいない)、
  maxLeverage 20×、刻み 0.1 単位
- HIP-3 の生態系: 稼働中の perp dex は 11(xyz, flx, vntl, hyna, km, abcd, cash, para, mkts, io, …)。
  xyz だけで 114 銘柄。新 dex・新銘柄の供給は続く(最初の 3 資産は無審査、以降ダッチオークション)
- 上場ライフサイクル(自前実測): スプレッドは初日 142.7bp → 99 日後 0.46bp。
  BBO 更新 4,930 → 345,789 回/日。市場の初期には「δ の 100 倍のスプレッド」が転がっている

## 5. 測定側の制約 — 我々のバックテストが現実とずれる点

| ずれ | 向き |
|---|---|
| 優先手数料時代(4/13〜)のデータを FIFO 前提で再現している。ALO コホート入札があると自分の新規注文は後回しにされうる | 楽観。ただし価格時間優先での約定再現率 96.97%(HANDOFF.md)なのでデータ窓では入札利用は限定的だったと推定 |
| 同ブロック内で取消がテイカーに先行する規則を織り込んでいない | 悲観(唯一) — 実物の stale 食いは我々の想定より 1 ブロック分難しい |
| 他者の反応・自分の板への影響なし | 楽観(報告 33 §7 から継承) |
| 発注拒否・接続断・congestion 条項なし | 楽観 |
| fills の ts は板より最大 ~1ms 早い(サブ ms の因果は主張しない) | 中立(METHODOLOGY §3) |
| Q=5 の遅延下 E[PnL] は未測定(遅延格子は Q≤1 のみ) | 不明 — 実弾判断の最優先測定 |

## 6. 対応方針

### 6-1. 却下される戦略(全て測定済みの根拠つき)

| 戦略 | 却下の根拠 |
|---|---|
| 速度依存のトップオブブック MM(現行シミュの形) | 遅延 50〜100ms で E[PnL] 負(報告 35)。到達可能遅延は 100ms 台以深(Glassnode 884ms)。敵は優先料でさらに ~360ms 買える。3 つの独立測定が同方向 |
| テイカーの方向当て | シグナル 1SD ≈ 0.05bp vs 費用 0.846bp + 半スプレッド(報告 16)。IOC 優先料で執行だけ速くしても元が取れない |
| 小口テスト運用(~100 USD) | 実仕様のレート制限が禁止(§2-3: k≤5 で予算超過、通る k≥10 は E[PnL]≈0)。「小さく試す」が構造的に不可能 — 試すなら Q≥1〜5 の資本を張るしかない |
| ALO 優先料で列を買う | 埋まり率 1〜2% × placement 課金 = 日次 630〜1,420 USD。論外(§1-3) |

### 6-2. 生き残る 3 方針

A. 置き型 MM の実装形(データ検証済みの範囲で最良)
`k=2 置き方策(価格が 2 tick 以上ずれたときだけ batchModify で建て直し)+ Q≥5 + 自前 API(builder fee 0)`
- 根拠: E[PnL] は k=0〜2 が最良(報告 37)。k≥2 は 400ms コホート入札の外側。
  Q≥5 でアドレス予算はどの解釈でも余裕(§2-3)。Q=5 の遅延ゼロ E[PnL] 中央値 30.76 USD/日(報告 33)
- 未検証のまま実弾にしてはならない点: Q=5 × 遅延 100ms × k 方策の E[PnL]。
  小 Q では遅延で符号が消えた。これを測るまで A は「候補」であって「推奨」ではない
- 経済性の上限: ~31 USD/日/市場(遅延ゼロ値)に対し、東京の実行系 + 監視で ~10 USD/日。
  単一市場では商売にならない。成立させる形は複数市場への横展開だけ(パイプラインは銘柄非依存)

B. 上場初期ライフサイクル MM(データ優位を最も活かせる仮説)
- 事実: DRAM 初日スプレッド 142.7bp、δ(0.363bp)の 390 倍。初期は板が薄く
  BBO 更新も 1/70(4,930 回/日)で、遅延もレースも効かない。HIP-3 は 11 dex・
  新銘柄の供給が続く(§4)

- 次の検証タスク(データは手元に完備): DRAM の 05-04〜05-11 を既存エンジンで再生し、
  初期版の E[PnL]・在庫リスク・約定量を実測する。数字が出るまで期待値は主張しない
- 既知のリスク: 初期は出来高も薄い(初日から数日の絶対額は小さい可能性)/
  混雑条項(前日メイカーシェア 0 で締め出し)/ 初期ボラの在庫リスク。全て検証項目
- 名前のない優位が一つ: 我々は HIP-3 上場初期の完全な L4 記録と再構成器を既に持つ。
  この検証を今日できる参加者はほぼいない

C. 遅延に鈍感な情報系(研究継続)
- トリガー密度・清算予測(L3 の (c) 系特徴量、L4 でしか作れない)— 地平が秒〜分で
  ブロック遅延に鈍感。★訂正(2026-08-19、報告 41): 「予測力は未検証」は誤り。
