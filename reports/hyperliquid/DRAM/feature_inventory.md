## 2. 作れる特徴量(families 別・約 45 個)

すべて 1 秒窓 $[T-\Delta,\; T)$ の集計、または T 時点の板の状態。
時間契約は `CLAUDE.md` の厳禁事項に従う(x は T までに確定、y は T 以降)。

### A. ウォレット / 参加者(10 個・全て新規)★L4 でしか作れない

| 特徴量 | 定義 |
|---|---|
| `n_users_new_bid` / `_ask` | その窓に新規注文を出した参加者数(側別) |
| `n_users_cancel` | 取消を出した参加者数 |
| `hhi_new_bid` / `_ask` | 新規注文数量のハーフィンダール指数 = Σ(シェア²) |
| `top1_share_new_bid` / `_ask` | 最大参加者のシェア |
| `net_flow_top1` | 最大参加者の(買い新規 − 売り新規)数量 |
| `user_churn` | 前窓と参加者集合の入替率(1 − Jaccard) |
| `n_users_best_bid` / `_ask` | 最良気配に並んでいる参加者数(book_px) |
| `top_user_share_best_bid` / `_ask` | 最良気配の最大参加者シェア |
| `user_conc_depth10` | 上位 10 段の `n_users` を数量加重平均 |

狙い: 1 者が板の 95% を出している市場で、その 1 者が引くかどうかは価格に直結する。
`top_user_share` の急変は「板が本当に薄くなる」瞬間の先行指標になりうる。

### B. トリガー注文(7 個・全て新規)★L4 でしか作れない

| 特徴量 | 定義 |

| `trigger_sz_above` / `_below` | 同・数量 |
| `trigger_dist_bp_above` / `_below` | `trigger_px` と mid の距離(数量加重平均) |
| `trigger_stock_5bp` / `_25bp` / `_100bp` | その時点で生きているトリガーの数量を距離帯別に累積 |
| `trigger_fired_n` | その窓で発火した(open→filled/canceled)トリガー数 |

狙い: ストップの蓄積は「どこまで下がると連鎖するか」を直接表す。

## 3. 一度作れば読まなくてよくなるもの / ならないもの

| テーブル | 集約後に読む必要 | 理由 |
|---|---|---|
| `cancel_grid` 2.7GB | 不要 | 既に窓集計。1 秒版を取り込めば役目は終わり |
| `flow_grid` 1.5GB | 不要 | 同上 |
| `queue_qi` 2.2GB | ほぼ不要 | §G を入れれば、注文単位で見たい時だけ |
| `book_px` 3.5GB | ほぼ不要 | §F で形状は尽きる。ただし新しい距離帯を足したくなったら要再読 |
| `lifecycle` 8.5GB | 条件つきで不要 | §A〜§E で主要なものは尽きるが、参加者×注文の関係(誰が誰の前に並ぶか、ユーザー間のクラスタリング)は集約すると復元不能 |

### 集約すると失われるもの(不可逆)

1. 不等間隔(イベント時間)での分析 — 1 秒に固定した時点で、ティック単位の分析はできない
2. 新しい QI の定義(例: 生存期間の時間加重平均)
3. 参加者間のネットワーク(A の直後に B が置く、といった順序関係)
4. 1 秒より細かい粒度(キャンセルは 100ms が最良だった)

→ 生データは消さず HDD に置く。目的は「読まなくて済む」であって「捨てる」ではない。
D: に 1.8TB 空きがあり、コールドデータの置き場としては十分
(HDD でも逐次読みは 74MB/s 出るので、年 1 回の再構築なら 18.4GB = 約 4 分)。

## 4. 出力の設計案

```
data/panel_full_1s/dt=YYYY-MM-DD/part-000.parquet
  ts + 既存 25 + 新規 45 = 約 70 列 × 8,466,661 行
  float32 主体で parquet+zstd ≈ 900MB〜1.2GB(SSD に置ける)
```

補助として、キャンセル・約定系だけ 100ms 版も出す(最良窓が 100ms だったため):

```
data/panel_flow_100ms/dt=…   ts + 約 15 列 × 8,470 万行 ≈ 2GB
```

見積り: `lifecycle` 4.47 億注文を参加者別に集計する §A が最も重く、
全体で 60〜90 分(SSD 上で実行した場合)。HDD 上だと §1 の実測(列射影で 45 倍)から
数時間かかるので、一度だけ SSD に置いて回すのが正解。

## 5. 実装順の提案

1. §B トリガー密度 — 指示書が主目的に挙げた成果物。単独で価値がある
2. §A ウォレット — もう 1 つの L4 固有。`top_user_share` 中央値 0.954 は異常に高く、
   単独でも報告価値がある
3. §C〜§E(lifecycle の残り)を同じ 1 パスで
4. §F(book_px)は別パス
5. §G/§H は既存テーブルの取り込みのみ

各段階でパネルに追記し、Lasso で選抜し直せば「新しい特徴量が既存を置き換えるか」を
そのつど確認できる。
